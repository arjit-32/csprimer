# Contributor Playbook & Platform Reference

**CSPrimer** is an open-source, interactive curriculum and knowledge base built to help engineers master foundational computer science, real-world full-stack development, and AI engineering from the ground up.

### About CSPrimer & Site Architecture

The curriculum is organized into **5 major learning tracks**:

- **Core-CS**: Operating systems, computer networks, computer architecture, databases, compilers, and foundational mechanics.
- **DSA**: Data structures, algorithms, complexity analysis, and interactive step-by-step problem visualizers.
- **Development**: Modern frontend, backend, fullstack frameworks, APIs, databases, and engineering workflows.
- **System-Design**: Distributed systems, microservices, cloud architectures, scaling patterns, and resilience.
- **AI-Engineering**: Machine learning foundations, LLM integrations, embeddings, and AI agents.

### Content Types on the Platform

1. **Course Series (`/courses`)**: Structured syllabi broken into logical chapters with progress tracking and sequential navigation.
2. **Hands-on Projects & Deep Dives (`/articles`)**: Standalone engineering tutorials, system blueprints, and practical implementations.
3. **Interview Bytes & Spaced Repetition (`/interview-bytes`, `/revision`)**: Flashcard-style interview questions with code solutions and Anki-style spaced review.
4. **Interactive Explorers**: Built-in algorithm visualizers (`<AlgoVisualizer>`), Git workflow simulators (`<GitVisualizer>`), and in-browser coding drills (`<TryCode>`).
5. **Shorts (`/shorts`)**: Bite-sized video explainers for rapid concept review.

---

1. **Local Scaffolding Tools**: One-click visual dashboard and terminal CLI to generate courses, roadmaps, and articles.

7. **Performance & Scale Engineering**: Micro-chunking for 500+ visualizers, memory leak prevention under ViewTransitions, and build optimizations.

## 2. Architecture & Metadata Rules

### The Core Hierarchy

The platform organizes content in a 3-tier hierarchy:

> **Category (Track)** ➔ **Series (Course)** ➔ **Articles (Lessons)**

| Level | Where Configured | Purpose |
| :--- | :--- | :--- |
| **1. Category / Track** | `src/config/roadmapOrder.json` | Top-level learning domain (`Core-CS`, `DSA`, `Development`, `System-Design`, `AI-Engineering`). |
| **2. Series / Course** | `src/content/series/<id>.json` | Structured course with a syllabus (`navbar`). Defines `"category": "<Track>"`. |
| **3. Lessons** | `src/content/articles/<slug>.md` | The actual educational lessons. Linked via `series: "<id>"`. |
| **Standalone Articles** | `src/content/articles/<slug>.md` | Independent tutorials or build projects. **Omit `series`**; categorized via `categories: [...]`. |

### Important Metadata Rules

1. **Course Lessons (`series` is set)**:
   - When an article has `series: "docker"`, its learning category is **inherited directly from the parent course**.
   - Lessons are grouped in the course syllabus and do not clutter the general `/articles` project listing.
2. **Standalone Articles (`series` is omitted)**:
   - Must specify `categories` using one or more of the 5 canonical categories below.
   - These are surfaced on `/articles` (Projects & Deep Dives).
3. **The 5 Canonical Categories**:
   - `"Core-CS"`: Operating systems, computer networks, computer architecture, databases, compilers.
   - `"DSA"`: Data structures, algorithms, complexity analysis, interview problem sets.
   - `"Development"`: Frontend, backend, fullstack frameworks, APIs, databases, tooling.
   - `"System-Design"`: Distributed systems, microservices, cloud architectures, scalability.
   - `"AI-Engineering"`: Machine learning, LLM integrations, embeddings, AI agents.

## 3. Step-by-Step Creation Playbooks

<Tabs>

<Tab name="1. Standalone Article">

### Adding a Standalone Article or Project

Use this for single-topic deep dives, project write-ups, or tutorials that do not belong to a sequential course syllabus.

#### Step 1: Create the markdown or MDX file
Create `src/content/articles/<your-article-slug>.md` (or `.mdx` if using custom components).

#### Step 2: Add Frontmatter
> **Important**: Do not add the `series` key for standalone articles.

```yaml
---
title: "Building an LRU Cache from Scratch in TypeScript"
description: "Learn cache eviction policies by implementing a doubly linked list + hash map cache."
categories: ["Development"]
author: "Arjit Sharma"
draft: false
featured: false
---
```

#### Step 3: Write Content
Write in standard Markdown or import MDX components (e.g. `<Notice>`, `<Badge>`, `<Accordion>`).

</Tab>

<Tab name="2. Course / Series">

### Adding a Multi-Lesson Series

A course requires connecting series metadata with lesson articles and roadmap ordering.

#### Step 1: Create the Series JSON
Create `src/content/series/<course-id>.json`.

```json
{
  "title": "System Design Essentials",
  "subtitle": "Architecting Scalable and Resilient Web Services",
  "description": "Learn load balancing, horizontal scaling, caching strategies, and data consistency models.",
  "category": "System-Design",
  "image": "../../assets/images/thumbnails/system-design.png",
  "weight": 10,
  "navbar": [
    {
      "subheading": "1. Foundations",
      "link": [
        { "type": "articles", "url": "intro-system-design", "title": "Introduction to System Design", "status": "in-progress" },
        { "type": "articles", "url": "load-balancing-basics", "title": "Load Balancing Patterns", "status": "planned" }
      ]
    }
  ]
}
```

*Status options*: `"planned"` (locked), `"in-progress"`, or `"re-visiting"`.

#### Step 2: Create the Lesson Articles
For each item in `navbar.link`, create the corresponding file in `src/content/articles/<url>.md`.
Ensure the `series` frontmatter value exactly matches `<course-id>`:

```yaml
---
title: "Introduction to System Design"
author: "Arjit Sharma"
series: "system-design-essentials"
categories: ["System-Design"]
draft: false
---
```

#### Step 3: Register in Roadmap Ordering
Open `src/config/roadmapOrder.json` and append `<course-id>` under the corresponding category array:

```json
{
  "System-Design": [
    "aws",
    "distributed",
    "system-design-essentials"
  ]
}
```

*(Or simply run `npm run admin` to perform all 3 steps automatically).*

</Tab>

<Tab name="4. Interview Byte">

### Adding an Interview Question

Interview questions power the **Interview Bytes** explorer and the **Anki Revision Modal**.

#### Step 1: Open or Create the Category YAML
Locate or create `src/content/interview-questions/<topic>.yaml` (e.g. `javascript.yaml`, `nodejs.yaml`).

#### Step 2: Append Question Entry

```yaml
questions:
  - id: 101
    tags: [javascript, closures, async]
    question: "Explain the Event Loop microtask vs macrotask execution order."
    answer:
      - "Synchronous code executes first on the call stack."
      - "Microtask queue (Promise callbacks, queueMicrotask) is completely drained before rendering."
      - "Macrotask queue (setTimeout, setInterval, I/O) executes one task per tick followed by microtasks again."
    code: |
      console.log('1');
      setTimeout(() => console.log('2'), 0);
      Promise.resolve().then(() => console.log('3'));
      console.log('4');
      // Output: 1, 4, 3, 2
```

<Tab name="5. TryCode Exercise">

### Adding an Interactive TryCode Coding Problem

TryCode embeds an in-browser code editor and automated test runner for frontend engineering drills.
> <Notice type="warning">TryCode is strictly reserved for frontend JavaScript/TypeScript and DOM interview challenges.</Notice>

#### Step 1: Choose Execution Mode

TryCode supports two distinct problem modes:
1. **`mode: "function"` (Default)**: Tests pure functions by invoking the user's exported function with test case arguments and asserting on returned values.
2. **`mode: "dom"`**: Provides initial HTML markup in an isolated sandbox. The user writes DOM manipulation code (event listeners, state updates), and test cases assert against live DOM state via `document.getElementById` or `document.querySelector`.

#### Step 2: Create Problem Definition File

Create `src/problems/frontend/<problem-id>.ts`:

##### Option A: Function Mode Example (`array-unique.ts`)

```typescript
import type { Problem } from "../../types/problem";

const problem: Problem = {
  id: "array-unique",
  title: "Remove Duplicates Preserving Order",
  mode: "function",
  starterCode: `function solution(nums) {
  // Return array with duplicates removed
  return [];
}`,
  tests: [
    { input: [[1, 2, 2, 3, 1, 4]], expected: [1, 2, 3, 4] },
    { input: [[5, 5, 5]], expected: [5] },
    { input: [[]], expected: [] },
  ],
};

export default problem;
```

##### Option B: DOM Mode Example (`counter-dom.ts`)

```typescript
import type { Problem } from "../../types/problem";

const problem: Problem = {
  id: "counter-dom",
  title: "Interactive Click Counter",
  mode: "dom",
  html: `<div id="counter-app">
  <span id="count">0</span>
  <button id="increment-btn">+1</button>
</div>`,
  starterCode: `// Attach click listener to increment counter
const btn = document.getElementById('increment-btn');
const countSpan = document.getElementById('count');

btn.addEventListener('click', () => {
  countSpan.textContent = String(Number(countSpan.textContent) + 1);
});`,
  tests: [
    {
      input: [],
      expected: 1,
      customCheck: `() => {
        const btn = document.getElementById('increment-btn');
        btn.click();
        return Number(document.getElementById('count').textContent);
      }`,
    },
  ],
};

export default problem;
```

#### Step 3: Embed in any MDX Article

```mdx
<TryCode problemId="array-unique" />
```

</Tab>

## 4. Complete Schemas & Type Reference

This section provides the static field definitions, types, defaults, and allowed values for every content collection defined in `src/content/config.ts`.

### 4.1 Articles Collection Schema
**Location:** `src/content/articles/*.md` or `*.mdx`  
**Purpose:** Standalone articles, project tutorials, and course lessons.

| Field | Type | Required | Default | Allowed Values / Constraints | Description |
| :--- | :--- | :---: | :--- | :--- | :--- |
| `title` | `string` | **Yes** | — | Non-empty string | Article title shown in headings and cards |
| `subtitle` | `string` | No | `undefined` | Any string | Secondary subhead for lessons or deep dives |
| `meta_title` | `string` | No | `undefined` | String (≤ 60 chars recommended) | SEO `<title>` tag override |
| `description` | `string` | No | `undefined` | String (≤ 160 chars recommended) | Meta and OpenGraph description |
| `image` | `string` | No | `undefined` | Relative path (e.g. `/images/og-image.jpg`) | Card thumbnail and social share preview |
| `author` | `string` | No | `undefined` | e.g. `"Arjit Sharma"` | Content author |
| `series` | `string` | No | `undefined` | Filename of series in `src/content/series/` | Links lesson to a course. **Omit for standalone articles** |
| `categories` | `string[]` | No | `["others"]` | `Core-CS`, `DSA`, `Development`, `System-Design`, `AI-Engineering` | Subject classification tag |
| `draft` | `boolean` | No | `false` | `true`, `false` | Excludes article from production builds when `true` |
| `year` | `number` | No | `undefined` | 4-digit year (e.g. `2025`) | Publishing / revision year |
| `featured` | `boolean` | No | `false` | `true`, `false` | Highlighted in hero card carousel |

#### TypeScript Interface
```typescript
export interface ArticleFrontmatter {
  title: string;
  subtitle?: string;
  meta_title?: string;
  description?: string;
  image?: string;
  author?: string;
  series?: string;
  categories: ("Core-CS" | "DSA" | "Development" | "System-Design" | "AI-Engineering" | "others")[];
  draft?: boolean;
  year?: number;
  featured?: boolean;
}
```

### 4.2 Series / Course Collection Schema
**Location:** `src/content/series/<course-id>.json`  
**Purpose:** Course metadata, syllabus chapters, and sidebar navigation hierarchy.

| Field | Type | Required | Default | Allowed Values / Constraints | Description |
| :--- | :--- | :---: | :--- | :--- | :--- |
| `title` | `string` | **Yes** | — | Non-empty string | Course display title |
| `subtitle` | `string` | No | `undefined` | Any string | Course tagline |
| `description` | `string` | **Yes** | — | Any string | Course summary on course overview cards |
| `image` | `string` | No | `undefined` | Path to thumbnail | Cover banner image |
| `category` | `string` | No | `"Course"` | `"Core-CS"`, `"DSA"`, `"Development"`, `"System-Design"`, `"AI-Engineering"` | Learning track bucket |
| `status` | `string` | No | `undefined` | `'planned'`, `'in-progress'`, `'re-visiting'` | Global course progress status (replaces legacy `ongoing`) |
| `ongoing` | `boolean \| string` | No | `false` | `true`, `false` | *(Deprecated)* Replaced by `status: "re-visiting"` / `"in-progress"` |
| `time` | `string` | No | `undefined` | e.g. `"4 hours"`, `"12 lessons"` | Estimated completion time |
| `weight` | `number` | No | `100` | Integer | Sort weight (lower appears first) |
| `navbar` | `Array<Section>` | **Yes** | — | Array of syllabus sections | Ordered chapters and lesson links (see below) |
| `resources` | `Array<Resource>` | No | `[]` | Array of supplementary references | Special "Further Learnings & Resources" section shown exclusively on individual course pages; excluded from roadmaps |

#### Navbar Structure (`navbar`)
Each section inside `navbar` contains:
- `subheading`: `string` (e.g. `"1. Foundations"`)
- `link`: Array of lesson links:
  - `type`: `"articles"` | `"external"`
  - `url`: `string` (article slug in `src/content/articles/` without `.md`, or external URL)
  - `title`: `string` (lesson title)
  - `status`: `'planned'` | `'in-progress'` | `'re-visiting'` (optional; `'planned'` displays a lock icon)

#### Resources Structure (`resources`)
Special section for supplementary external courses, official docs, books, or handwritten notes.
- **Where it appears**: Exclusively on `/courses/[course]`.
- **Roadmap exclusion**: Excluded from roadmaps, drawer checklists, and completion percentages.
- **Editable in Studio**: Tab 2 of `npm run admin` allows 1-click adding, editing, reordering, and saving.
- Each entry contains:
  - `title`: `string` (e.g. `"Alex Aiken - Stanford lectures"`)
  - `url`: `string` (External URL `https://...` or internal article path `/articles/<slug>`)
  - `description`: `string` (optional note or caption)

#### TypeScript Interface
```typescript
export type CourseStatus = 'planned' | 'in-progress' | 're-visiting';

export interface SeriesNavbarLink {
  type: 'articles' | 'external';
  url: string;
  title: string;
  status?: CourseStatus;
}

export interface SeriesNavbarSection {
  subheading: string;
  link: SeriesNavbarLink[];
}

export interface CourseResource {
  title: string;
  url: string;
  description?: string;
}

export interface SeriesData {
  title: string;
  subtitle?: string;
  description: string;
  image?: string;
  category: string;
  ongoing?: boolean | string;
  status?: CourseStatus;
  time?: string;
  weight: number;
  navbar: SeriesNavbarSection[];
  resources?: CourseResource[];
}
```

### 5.4 Accordions (`<Accordion>`)

Expandable accordion container for FAQs, solutions, or deep-dive collapsible explanations.

<Accordion title="When should I use a Series instead of a Standalone Article?">

Create a **Series** when:
- The content consists of multiple sequential lessons or chapters.
- You need a persistent sidebar navigation and previous/next chapter progression.
- The course belongs to a categorized learning path on `/roadmaps`.

Create a **Standalone Article** when:
- It is a single project, quick tutorial, or independent deep dive.
- It does not require a sidebar syllabus.

</Accordion>

<Accordion title="How do I mark a lesson as planned/locked in a course?">

In `src/content/series/<id>.json`, set `"status": "planned"` on the link object:

```json
{
  "type": "articles",
  "url": "distributed-consensus",
  "title": "Distributed Consensus (Raft & Paxos)",
  "status": "planned"
}
```

This displays the lesson with a lock icon and disables navigation until it is published.

</Accordion>

## 7. Algorithm Visualizer: AI Prompt & Generator Guide

This section provides the complete reference specification and copy-paste prompt template to generate interactive algorithm visualizers for any DSA problem (Sorting, Searching, HashMaps, Sets, Queues, Deques, Trees, Heaps, Stacks, Linked Lists, DP) using any AI assistant (ChatGPT, Claude, Gemini, Cursor, Antigravity).

### 7.1 Visualizer Architecture Overview

The visualizer system is composed of:
- **Engine Component**: `<AlgoVisualizer problemId="slug" />` in `src/components/features/visualizer/AlgoVisualizer.astro`.
- **Step Builder**: `StepBuilder` class in `src/problems/algorithms/builder.ts` with a fluent `.step({ ... })` API.
- **Type Definitions**: `src/problems/algorithms/types.ts` defining all state models and render options.
- **Algorithm Directory**: All algorithm definition files live in `src/problems/algorithms/<slug>.ts`.
- **Registry**: `src/problems/algorithms/index.ts` (automatically updated via `syncAlgorithmIndex()`).

### 7.2 Representation of All DSA Problem Types

The visualization engine supports representing any DSA problem type through flexible combinations of data structures:

| DSA Problem Type | How to Represent with `StepBuilder` | Key Properties Used |
| :--- | :--- | :--- |
| **Merge Sort** | Subarrays via `arrays: [left, right, merged]` or single array with `window: [low, high]` and merge pointers `i, j, k` | `arrays` or `array.window`, `pointers` |
| **Quick Sort** | Single array with partition pointers (`low`, `pivot`, `high`, `i`, `j`), swap highlights, and sub-range windows | `pointers`, `highlights`, `window` |
| **Binary Search** | Single array with `low`, `mid`, `high` pointers, active search interval `window: [low, high]`, and match highlights | `pointers: { low, mid, high }`, `window: [low, high]` |
| **Linear Search** | Scanning pointer `i` checking each element with match/visited state highlights | `pointers: { i }`, `highlights` |
| **Hash Map** | Key-Value dictionary with `searchKey` and status banner (`found`, `not-found`, `searching`) | `hashmap: Map or Record`, `searchKey`, `searchResult` |
| **Set / HashSet** | Unique element collection with `searchElement` and membership verification banner (`contains(x)`) | `set: Set or string[] or number[]`, `searchElement`, `searchResult` |
| **Queue (FIFO)** | First-In-First-Out queue with FRONT and REAR markers, showing enqueue at rear and dequeue at front (BFS) | `queue: { items: [...], action: 'enqueue' \| 'dequeue', label: 'Queue (FIFO)' }` |
| **Deque (Double Queue)** | Double-ended queue with front (`addFirst`/`removeFirst`) and back (`addLast`/`removeLast`) markers (e.g. Monotonic Deque, Sliding Window Max) | `deque: { items: [...], action: 'addFirst' \| 'removeFirst' \| 'addLast' \| 'removeLast', label: 'Double-Ended Queue (Deque)' }` |
| **Stack (LIFO)** | Last-In-First-Out container with vertical layout, TOP marker, depth count, and push/pop animations (brackets, monotonic stack) | `stack: { items: [...], action: 'push' \| 'pop', label: 'Stack (LIFO)' }` |
| **Binary Tree & BST** | Node hierarchy with parent-child links, traversal highlights, and search targets | `tree: { nodes: [...], rootId }` |
| **Tree + Array (Heaps)** | Both `array` and `tree` in the exact same step, mapping array index `i` to tree nodes with children at `2i + 1` and `2i + 2` | `array: { ... }`, `tree: { ... }` |
| **Linked List** | Node chains with `next` pointers, head/curr/prev markers, and node reversal indicators | `linkedList: { nodes: [...], headId }` |
| **Dynamic Programming** | 1D or 2D state matrix with active computation cell, dependency cell highlights, and transition formula banner | `dpTable: { grid, activeCell, highlightCells, formula }` |

> [!TIP] Stack vs. Queue vs. Deque Selection
> - **Stack (LIFO)**: Use `step.stack`. Renders as a vertical container with a `TOP` marker and `push`/`pop` operations.
> - **Queue (FIFO)**: Use `step.queue`. Renders as a horizontal pipeline with `← FRONT (Out)` on the left and `REAR (In) ←` on the right with `enqueue`/`dequeue` operations.
> - **Deque (Double-Ended)**: Use `step.deque`. Renders with both `FRONT` and `BACK` markers, supporting `addFirst`, `removeFirst`, `addLast`, and `removeLast`.
> In the CMS Visual Step Builder, simply pick your desired data structure from the **Container Type** dropdown.

### 7.3 Core Authoring Rules

1. **Idiomatic Java in `codeLine`**: Always display the actual, readable Java statement executed at that step.
2. **Pointers Only (No Window Text Badges)**: Arrays show labeled pointer arrows (`i`, `j`, `low`, `mid`, `high`, `left`, `right`). Windows outline the active subarray boundary (`window: [start, end]`). **Never put text labels or badge strings on or inside windows.**
3. **Variable Tracking in Header**: Keep all numeric metrics, accumulators, sums, and status flags in `variables: { ... }`. They render in a clean, dedicated bar above the visualization.
4. **Freeform Categories**: Category is an open string (e.g. `'Sorting'`, `'Sliding Window'`, `'Two Pointers'`, `'Trees & Heaps'`, or `'General DSA'`).
5. **No Forced Complexity / Difficulty Tags**: The visualizer player stays clean, focused entirely on the execution flow and intuitive mental model.

### 7.5 Reference Implementation Blueprints

#### Blueprint 1: Binary Search (Array + Pointers + Search Window)

```typescript
import type { AlgorithmDefinition, ExecutionStep } from './types';
import { StepBuilder } from './builder';

export const binarySearch: AlgorithmDefinition = {
  id: 'binary-search',
  title: 'Binary Search',
  category: 'Searching',
  description: 'Searches for a target value within a sorted array by halving the search space each step.',
  visualizationTypes: ['array'],
  defaultInputs: {
    nums: [2, 5, 8, 12, 16, 23, 38, 56, 72, 91],
    target: 23,
  },
  inputSchema: [
    {
      name: 'nums',
      label: 'Sorted Array (comma-separated)',
      type: 'number-array',
      defaultValue: [2, 5, 8, 12, 16, 23, 38, 56, 72, 91],
      placeholder: '2, 5, 8, 12, 16, 23, 38, 56, 72, 91',
      description: 'Ascending sorted array',
    },
    {
      name: 'target',
      label: 'Target Value',
      type: 'number',
      defaultValue: 23,
      placeholder: '23',
      description: 'Number to search for',
    },
  ],
  generateSteps: (inputs: Record<string, any>): ExecutionStep[] => {
    const rawNums = inputs.nums;
    const nums: number[] = Array.isArray(rawNums)
      ? rawNums.map(Number).filter((n) => !isNaN(n))
      : [2, 5, 8, 12, 16, 23, 38, 56, 72, 91];
    const target = Number(inputs.target ?? 23);

    const builder = new StepBuilder();
    let low = 0;
    let high = nums.length - 1;

    builder.step({
      title: 'Initialize Binary Search',
      description: `Target is ${target}. Set low = 0 and high = ${high}.`,
      codeLine: 'int low = 0, high = nums.length - 1;',
      variables: { low, high, target },
      array: {
        values: [...nums],
        pointers: { low, high },
        window: [low, high],
        label: 'nums[]',
      },
    });

    while (low <= high) {
      const mid = Math.floor((low + high) / 2);
      const midVal = nums[mid];

      builder.step({
        title: `Calculate Midpoint: mid = ${mid} (nums[mid] = ${midVal})`,
        description: `Inspect middle element at index ${mid}.`,
        codeLine: 'int mid = low + (high - low) / 2;',
        variables: { low, mid, high, 'nums[mid]': midVal, target },
        array: {
          values: [...nums],
          pointers: { low, mid, high },
          highlights: [mid],
          window: [low, high],
          label: 'nums[]',
        },
      });

      if (midVal === target) {
        builder.step({
          title: `Target Found at Index ${mid}!`,
          description: `nums[${mid}] == ${target}. Return index ${mid}.`,
          codeLine: 'if (nums[mid] == target) return mid;',
          variables: { low, mid, high, resultIndex: mid, status: 'FOUND' },
          array: {
            values: [...nums],
            pointers: { mid },
            highlights: [{ index: mid, state: 'match' }],
            label: 'nums[]',
          },
        });
        return builder.build();
      } else if (midVal < target) {
        builder.step({
          title: `nums[mid] = ${midVal} < ${target}: Discard Left Half`,
          description: `Target must lie in the right half. Move low to mid + 1.`,
          codeLine: 'low = mid + 1;',
          variables: { low: mid + 1, mid, high, target },
          array: {
            values: [...nums],
            pointers: { low: mid + 1, high },
            window: [mid + 1, high],
            label: 'nums[]',
          },
        });
        low = mid + 1;
      } else {
        builder.step({
          title: `nums[mid] = ${midVal} > ${target}: Discard Right Half`,
          description: `Target must lie in the left half. Move high to mid - 1.`,
          codeLine: 'high = mid - 1;',
          variables: { low, mid, high: mid - 1, target },
          array: {
            values: [...nums],
            pointers: { low, high: mid - 1 },
            window: [low, Math.max(low, mid - 1)],
            label: 'nums[]',
          },
        });
        high = mid - 1;
      }
    }

    builder.step({
      title: 'Target Not Found',
      description: `Search space exhausted (low > high). Target ${target} is not in the array.`,
      codeLine: 'return -1;',
      variables: { low, high, target, status: 'NOT FOUND' },
      array: { values: [...nums], label: 'nums[]' },
    });

    return builder.build();
  },
};

export default binarySearch;
```

#### Blueprint 2: Sliding Window Maximum (Array + Double Queue / Deque)

```typescript
import type { AlgorithmDefinition, ExecutionStep } from './types';
import { StepBuilder } from './builder';

export const slidingWindowMax: AlgorithmDefinition = {
  id: 'sliding-window-maximum',
  title: 'Sliding Window Maximum',
  category: 'Deques & Sliding Window',
  description: 'Maintains a monotonic decreasing deque storing indices to find the maximum in each sliding window in O(N) time.',
  visualizationTypes: ['array', 'deque'],
  defaultInputs: {
    nums: [1, 3, -1, -3, 5, 3, 6, 7],
    k: 3,
  },
  inputSchema: [
    {
      name: 'nums',
      label: 'Array',
      type: 'number-array',
      defaultValue: [1, 3, -1, -3, 5, 3, 6, 7],
      placeholder: '1, 3, -1, -3, 5, 3, 6, 7',
      description: 'Input numbers array',
    },
    {
      name: 'k',
      label: 'Window Size (k)',
      type: 'number',
      defaultValue: 3,
      placeholder: '3',
      description: 'Sliding window width',
    },
  ],
  generateSteps: (inputs: Record<string, any>): ExecutionStep[] => {
    const rawNums = inputs.nums;
    const nums: number[] = Array.isArray(rawNums)
      ? rawNums.map(Number).filter((n) => !isNaN(n))
      : [1, 3, -1, -3, 5, 3, 6, 7];
    const k = Math.max(1, Number(inputs.k ?? 3));

    const builder = new StepBuilder();
    const deque: number[] = []; // Stores indices
    const result: number[] = [];

    builder.step({
      title: 'Initialize Monotonic Deque',
      description: `Create an ArrayDeque to store indices of potential maximum elements in decreasing value order.`,
      codeLine: 'Deque<Integer> deque = new ArrayDeque<>();',
      variables: { k, dequeSize: 0 },
      array: { values: [...nums], pointers: { i: 0 }, label: 'nums[]' },
      deque: [],
    });

    for (let i = 0; i < nums.length; i++) {
      // Remove elements outside current window
      while (deque.length > 0 && deque[0] < i - k + 1) {
        const removed = deque.shift()!;
        builder.step({
          title: `deque.removeFirst(): Out of Window`,
          description: `Index ${removed} falls outside window [${i - k + 1}, ${i}]. Remove from front.`,
          codeLine: 'if (!deque.isEmpty() && deque.peekFirst() < i - k + 1) deque.pollFirst();',
          variables: { i, removedIndex: removed, 'deque.size()': deque.length },
          array: { values: [...nums], pointers: { i }, window: [Math.max(0, i - k + 1), i], label: 'nums[]' },
          deque: deque.map((idx) => `idx ${idx} (${nums[idx]})`),
        });
      }

      // Remove smaller elements from back
      while (deque.length > 0 && nums[deque[deque.length - 1]] < nums[i]) {
        const removed = deque.pop()!;
        builder.step({
          title: `deque.removeLast(): Monotonic Violation`,
          description: `nums[${removed}] (${nums[removed]}) < nums[${i}] (${nums[i]}). Pop from back.`,
          codeLine: 'while (!deque.isEmpty() && nums[deque.peekLast()] < nums[i]) deque.pollLast();',
          variables: { i, poppedIndex: removed, currentVal: nums[i] },
          array: { values: [...nums], pointers: { i }, highlights: [i, removed], window: [Math.max(0, i - k + 1), i], label: 'nums[]' },
          deque: deque.map((idx) => `idx ${idx} (${nums[idx]})`),
        });
      }

      deque.push(i);
      builder.step({
        title: `deque.addLast(${i}): Added Current Index`,
        description: `Pushed index ${i} (value ${nums[i]}) to back of deque.`,
        codeLine: 'deque.offerLast(i);',
        variables: { i, currentVal: nums[i], windowMax: nums[deque[0]] },
        array: { values: [...nums], pointers: { i }, window: [Math.max(0, i - k + 1), i], label: 'nums[]' },
        deque: deque.map((idx) => `idx ${idx} (${nums[idx]})`),
      });

      if (i >= k - 1) {
        result.push(nums[deque[0]]);
        builder.step({
          title: `Record Window Maximum: ${nums[deque[0]]}`,
          description: `Window [${i - k + 1}, ${i}] maximum is at front of deque: nums[${deque[0]}] = ${nums[deque[0]]}.`,
          codeLine: 'result[i - k + 1] = nums[deque.peekFirst()];',
          variables: { windowStart: i - k + 1, windowEnd: i, max: nums[deque[0]], resultSoFar: [...result] },
          array: { values: [...nums], pointers: { max: deque[0] }, window: [i - k + 1, i], highlights: [deque[0]], label: 'nums[]' },
          deque: deque.map((idx) => `idx ${idx} (${nums[idx]})`),
        });
      }
    }

    return builder.build();
  },
};

export default slidingWindowMax;
```

## 9. Performance & Scale Engineering Guide

This section explains how the platform achieves sub-second builds and fluid client transitions while scaling from 300 to 800+ articles and 200–500 DSA problem visualizers.

### 9.1 Dynamic Micro-Chunking for 200–500 DSA Visualizers

#### The Problem:
If an Astro site statically imports hundreds of algorithm definitions, Vite bundles them into a single monolithic JavaScript file (`index.*.js`). Every page visitor would download the code for all 500 algorithms, causing massive bundle bloat and sluggish first-contentful paint.

#### The Architectural Solution:
In `src/components/features/visualizer/engine/visualizer-controller.ts`:
- Negative globs exclude internal builder utilities from the loader:
  ```typescript
  const modules = import.meta.glob([
    '../../../../problems/algorithms/*.ts',
    '!**/index.ts',
    '!**/builder.ts',
    '!**/types.ts'
  ]);
  ```
- Each algorithm compiles into its own independent micro-chunk (`~2–3 KB` each, e.g. `02-two-sum.*.js`).
- When a user navigates to an article containing `<AlgoVisualizer problemId="two-sum" />`, only that single micro-chunk is fetched asynchronously on demand.
- Adding 500 new DSA articles has **zero impact** on the base client bundle size.

---

### 9.2 Main-Thread Infinite Loop & Memory Guardrails

To protect against browser lockups during user testing or complex recursions:
- **`MAX_STEPS = 300`**: Enforced in `StepBuilder.addStep()` (`src/problems/algorithms/builder.ts`).
- If an algorithm enters a runaway loop or excessive state transitions on custom user inputs, step generation halts safely with a console warning rather than crashing the visitor's browser tab.

---

### 9.3 Client-Side SPA Lifecycle & ViewTransitions Safety

Astro's `<ViewTransitions />` turns navigation into a client-side Single Page Application (SPA). The HTML `<body>` is swapped while JavaScript globals (`window`, `document`) persist.

#### Contributor Rules for Client Scripts:

1. **Always Listen to `astro:page-load`**:
   - ❌ Never use `document.addEventListener("DOMContentLoaded", init)` alone (it will not fire when navigating between pages).
   - ❌ Never run `init()` at module top-level AND in `astro:page-load` (causes double-initialization).
   - ✅ Always use:
     ```javascript
     document.addEventListener("astro:page-load", () => {
       initComponent();
     });
     ```

2. **Always Clean Up Global Window & Document Listeners**:
   - Attaching anonymous listeners to `window` or `document` inside an `astro:page-load` hook creates memory leaks and duplicate triggers on every page visit.
   - **Pattern A: AbortController (Recommended)**
     ```javascript
     let abortController = new AbortController();

     document.addEventListener("astro:before-swap", () => {
       abortController.abort();
       abortController = new AbortController();
     });

     window.addEventListener("resize", handleResize, { signal: abortController.signal });
     ```
   - **Pattern B: Named Handler Unmounting**
     ```javascript
     window.removeEventListener("keydown", window.__myHandlerRef);
     window.__myHandlerRef = handleKeyDown;
     window.addEventListener("keydown", handleKeyDown);
     ```

3. **Debounce Scroll & Resize with `requestAnimationFrame`**:
   - In components like `TableOfContents.astro`, scroll calculations are wrapped in `requestAnimationFrame` to eliminate layout thrashing and maintain 60 FPS scrolling.

---

### 9.4 Google Analytics 4 (GA4) Virtual Pageview Tracking

Because Astro swaps page content without a full document reload:
- Standard GA4 tracking tags only fire on the initial hard page load.
- In `src/layouts/Base.astro`, an `astro:page-load` listener dispatches virtual `page_view` events:
  ```javascript
  let isFirstLoad = true;
  document.addEventListener("astro:page-load", () => {
    NProgress.done();
    if (isFirstLoad) {
      isFirstLoad = false;
      return;
    }
    if (typeof window.gtag === "function") {
      window.gtag("event", "page_view", {
        page_location: window.location.href,
        page_title: document.title,
      });
    }
  });
  ```
- This ensures 100% accurate traffic analytics across all 500+ articles without double-counting the initial visit.
