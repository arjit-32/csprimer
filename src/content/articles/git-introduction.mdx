## 1. What is Version Control?

Version control systems (VCS) track and coordinate modifications to a codebase over time. They allow software engineers to review historical snapshots, revert mistakes, and collaborate seamlessly across teams.

Earlier systems like **CVS** and **SVN** relied on a centralized architecture: a single central repository held the complete history of the code. If that server was unreachable, developers could not record commits or review past versions.

**Git is a distributed version control system (DVCS)**. Every developer maintains a full-fidelity, independent local repository on their machine—complete with the entire commit history and branch graph. Developers commit, branch, and review history entirely offline, synchronizing with remote repositories (such as GitHub) only when ready.

## 2. Phases of Git Content

![image.png](https://res.cloudinary.com/dwa6rcttw/image/upload/f_auto,q_auto,w_800/v1741776562/image_wem8sa.png)

Git organizes files into three main phases:

1. **Working Directory (Working Tree)**: The local project folder where files are modified. Changes here are unstaged.
2. **Staging Area (Index)**: A temporary staging area where changes are collected and prepared with `git add` before committing.
3. **Git Repository**: The permanent database inside the `.git` directory where committed snapshots are recorded.

## 3. How Git Records Changes: Commits as Snapshots

![image.png](https://res.cloudinary.com/dwa6rcttw/image/upload/f_auto,q_auto,w_800/v1741776562/image_1_zzoyef.png)

Unlike legacy systems that track file-by-file delta diffs, Git stores its history as a series of **complete snapshots** of the codebase:

- Commit **C** depends on parent commit **B**.
- Commit **B** depends on parent commit **A**.

Each commit contains:
- A cryptographic **SHA-1 hash** (e.g. `a1b2c3d`) ensuring security and immutability.
- A pointer to its **parent commit(s)**, establishing an unbroken, verifiable historical chain (A → B → C).
- Author metadata, timestamp, and a descriptive message.

A branch allows developers to work on different versions of the project simultaneously. Instead of modifying the main codebase directly, changes can be made in a separate branch and later merged.

## 5. What is GitHub?

While Git is the command-line version control tool running locally on your computer, **GitHub** is a remote hosting service commonly used by teams as a centralized upstream repository. Developers push their local changes to GitHub and pull team updates from it, using pull requests to discuss and review code.

---

## 6. How is Git Different from Other Systems?

- **Fast Branching**: Branching in Git takes constant `O(1)` time, whereas CVS and SVN require duplicating files in `O(N)` time.
- **Project Snapshots**: Git stores changes as complete snapshots of the entire project, rather than tracking file-by-file diffs like older systems.
- **Cryptographic Integrity**: Changes are identified by cryptographic hash numbers (e.g. `a1b2c3d4`) instead of arbitrary version numbers, ensuring tamper-proof security.

## 7. Inside the `.git` Directory: How Git Stores Everything

When you initialize a repository with `git init`, Git creates a hidden `.git` folder. This is Git's complete database:

| Component | Description |
| :--- | :--- |
| **`HEAD`** | Text file pointing to your active branch (e.g. `ref: refs/heads/main`). |
| **`refs/heads/`** | Small 41-byte text files holding the exact commit SHA for each branch pointer. |
| **`index`** | Binary cache file representing the Staging Area between disk and repository. |
| **`objects/`** | Content-addressable object store holding **Blobs** (files), **Trees** (directories), and **Commits** (snapshots). |

Because branches and tags are just tiny text files holding a 40-character hash, branching, tagging, and switching operations are virtually instant!
